§ 1.0

Attack Surface Inventory

Enumerated attack surface across five architectural layers of autonomous DevSecOps agent pipelines. Each layer presents distinct threat vectors requiring targeted mitigations.

L-01 Code Generation Layer
  • LLM Prompt Injection — Adversarial instructions embedded in PR comments, issue tracker content, or ingested documentation that redirect agent code-generation behavior to produce malicious outputs or suppress security findings.
  • Training Data Poisoning — Contamination of fine-tuning corpora or RAG retrieval stores with crafted vulnerable code patterns, causing systematic generation of exploitable outputs at scale across all agent consumers.
  • Hallucinated Dependencies — LLM-generated package references that do not exist in legitimate registries, exploitable via dependency squatting where attackers pre-register the hallucinated names with malicious payloads.
  • Context Window Overflow — Injection of oversized context payloads designed to evict prior system prompt constraints, artificially expanding the agent's effective permission envelope during generation.
L-02 Pipeline Execution Layer
  • CI/CD Agent Takeover — Exploitation of over-permissioned pipeline execution agents to hijack build steps, inject arbitrary shell commands, or exfiltrate secrets from runner environments via prompt injection or malicious task input.
  • Privilege Escalation — Leveraging pipeline agent credentials (GITHUB_TOKEN, OIDC tokens) to escalate from repository-scoped access to organization-wide or cloud IAM permissions beyond the pipeline's intended operational scope.
  • Tool Misuse — Autonomous agents invoking registered tools (file system writes, network calls, package installs) outside their intended scope, whether via prompt injection, emergent behavior, or malicious tool schema manipulation.
  • Runner Environment Persistence — Malicious artifacts introduced into shared runner caches, workspace volumes, or container layers to achieve cross-build persistence and affect subsequent pipeline runs.
L-03 Supply Chain Layer
  • Malicious Package Suggestion — Agent recommends or autonomously installs packages with known malicious payloads, compromised maintainer accounts, or malware in post-install scripts without validation against reputation signals.
  • SBOM Tampering — Manipulation of Software Bill of Materials artifacts generated or consumed by agents, obscuring dependency provenance and enabling silent introduction of vulnerable or malicious components.
  • Dependency Confusion — Exploitation of package resolution order ambiguities when agents suggest internal package names that can be shadowed by attacker-controlled public registry entries with higher version numbers.
  • Registry Poisoning — Compromise of agent-trusted package registries or mirrors to serve trojanized versions of legitimate packages referenced in AI-generated code recommendations.
L-04 Orchestration Layer
  • Multi-Agent Trust Violations — Absence of inter-agent authentication or authorization boundaries allowing a compromised sub-agent to impersonate an orchestrator, forge task delegations, or inject adversarial instructions into sibling agent contexts.
  • MCP Server Abuse — Exploitation of Model Context Protocol server vulnerabilities or misconfigurations to serve adversarial tool responses, manipulate tool definitions at registration time, or exfiltrate agent context data.
  • Memory Poisoning — Persistent injection of adversarial data into agent memory stores (vector DBs, conversation history, scratchpad files) to influence future agent behavior across sessions and builds.
  • Orchestrator Token Flooding — Denial-of-service through token exhaustion or context flooding attacks against orchestration LLMs, degrading pipeline throughput and potentially triggering fallback to degraded, less-secure execution modes.
L-05 Output / Deploy Layer
  • Insecure IaC Generation — AI-generated Infrastructure-as-Code containing misconfigured IAM policies, publicly exposed storage buckets, disabled encryption at rest, or overly permissive network security groups that pass functional tests while violating security baselines.
  • Secrets in Generated Artifacts — Hardcoded credentials, API keys, or cryptographic material embedded in AI-generated source files, configuration templates, container images, or deployment manifests — either hallucinated or injected.
  • Unsigned Pipeline Outputs — Artifacts generated or modified by agents (container images, release binaries, IaC modules, SBOMs) published without cryptographic signing, enabling undetectable tampering at delivery or deployment time.
  • Compliance Drift — AI-generated configurations that satisfy functional requirements while silently violating security policy baselines (PCI DSS, SOC 2, CIS Benchmarks), creating audit risk and exploitable exposure undetected until review.

Prompt Injection via Code Review Feedback Loop
Attack Vector
An adversary submits a PR containing crafted text in inline review comments, commit messages, or linked issue descriptions that embed injection directives. When the AI code review agent ingests this as context, the injected instructions override system-level constraints — causing the agent to approve insecure code, suppress security findings, or propose malicious modifications to CI workflow files (.github/workflows/).

AI Review Agent → CI/CD Pipeline Trigger → GITHUB_TOKEN Scope
Likelihood
High — No specialized access required; exploitable by any PR contributor on any public repository

Integrity Confidentiality Privilege Gain
T-02 High
CVSS 8.4
Hallucinated Dependency Supply Chain Attack
Attack Vector
An LLM code generation agent suggests a plausible-but-nonexistent package name (e.g., requests-oauth2-helper). An attacker pre-registers this name on PyPI/npm with a malicious post-install hook. When the agent autonomously runs pip install or adds the name to requirements.txt, the trojanized package executes during build — exfiltrating secrets or establishing backdoor persistence in the runner.
Affected Component
Package Registry (PyPI/npm) → Agent Tool: shell/install → Build Environment
Likelihood
Medium — Requires hallucination event + attacker name registration; incidence rising with LLM-assisted coding adoption rates
Impact Profile
Confidentiality Integrity Availability
T-03 Critical
CVSS 9.1
Autonomous Agent Privilege Escalation in CI/CD
Attack Vector
A DevSecOps agent operating with contents: write and id-token: write GitHub Actions permissions is manipulated via prompt injection or malicious task input to request an OIDC identity token for cloud provider authentication. The agent then assumes an IAM role with broader privileges than required, enabling lateral movement to cloud resources, cross-account operations, or secret store exfiltration outside the intended pipeline boundary.
Affected Component
GitHub Actions Runner → OIDC Token Provider → Cloud IAM Role → Production Resources
Likelihood
Medium — Requires over-permissioned pipeline setup; extremely common in early-stage agentic DevSecOps deployments
Impact Profile
Privilege Escalation Confidentiality Integrity Availability
T-04 Critical
CVSS 9.3
MCP Server Compromise Leading to Pipeline Takeover
Attack Vector
An attacker compromises or stands up a malicious Model Context Protocol (MCP) server trusted by the orchestration agent for tool definitions. The rogue server returns trojanized tool schemas, poisoned execution responses, or fabricated read results — causing the agent to delete resources, exfiltrate data, or disable security controls while believing it is executing legitimate pipeline steps. Absence of MCP server identity verification makes this transparent to the agent.
Affected Component
MCP Server → Agent Tool Registry → Pipeline Orchestrator → All Downstream Tools
Likelihood
Medium — MCP adoption is early-stage; authentication gaps are well-documented and the attack surface grows as adoption scales
Impact Profile
Full Takeover Confidentiality Integrity Availability
T-05 Medium
CVSS 7.2
AI-Generated IaC with Embedded Backdoor Secrets
Attack Vector
An AI agent generating Terraform or CloudFormation templates either (a) hallucinates hardcoded credentials in resource definitions, (b) is injected with instructions to embed specific API keys, or (c) generates default-insecure configurations (cidr: 0.0.0.0/0, public S3 buckets, disabled KMS). These pass automated validation if static analysis gates are absent, deploying attacker-accessible backdoors into production infrastructure undetected.
Affected Component
IaC Generator Agent → Terraform / CloudFormation Module → Cloud Infrastructure
Likelihood
Medium-High — Hallucinated secrets are a documented LLM behavior; detection requires explicit, correctly-configured pipeline gates
Impact Profile
Confidentiality Integrity

▶ T-01 Prompt Injection via Code Review Feedback Loop High
Preventive Controls
  • Schema-validate and sanitize all ingested PR metadata before inclusion in agent context windows; treat PR content as untrusted user-tier input, never as system instructions
  • Enforce instruction hierarchy: system prompts must be structurally non-overridable by user-tier content; apply architectural separation between trusted and untrusted context slots
  • Apply LLM output classifiers to detect injection artifacts in agent decisions before any write-back action is taken on the repository
  • Enforce read-only agent access to PR comment data; require explicit human gate for any agent-generated write operations to CI configuration files
  • Implement prompt templates with explicit injection-resistance patterns; version control all system prompts as security-relevant artifacts
Detective Controls
  • Log complete agent context windows before LLM inference; retain in tamper-evident storage for anomaly correlation and incident investigation
  • Monitor agent approval/rejection decision ratios with statistical outlier alerting; flag sudden reversals of prior security assessments
  • Cross-validate agent code review findings against independent SAST output; alert on significant divergence between agent and tool-based findings
  • Instrument agent output for injection signatures: unexpected shell commands, URL exfiltration patterns, or base64-encoded payloads in generated content
  • Maintain audit trail linking every agent decision to the specific context window hash that produced it
Responsive Controls
  • Automatically quarantine PRs that triggered injection detection events; block merge pending mandatory human security review
  • Immediately revoke agent write permissions upon detection of anomalous approval patterns; escalate to security team
  • Rotate any secrets potentially accessible during the injection event window; audit repository access logs for exfiltration indicators
  • Replay affected pipeline steps with validated, sanitized context after root cause identification and remediation

▶ T-02 Hallucinated Dependency Supply Chain Attack High
Preventive Controls
  • Validate all agent-suggested package names against an approved internal registry allowlist before any installation; reject any package not present in the allowlist without explicit human override
  • Implement OSSPolicyGuard-pattern dependency validation: verify package existence, publish age, download velocity, maintainer count, and OpenSSF Scorecard score before agent auto-install authorization
  • Pin all dependencies to cryptographic hashes (SHA-256); reject any agent-proposed unpinned dependency additions in pipeline gates
  • Enforce private package mirror with allowlist; block direct public registry access from pipeline runners via network egress policy
  • Prohibit agents from executing install commands without human-in-the-loop confirmation when package risk score exceeds configured threshold
Detective Controls
  • Generate and diff SBOMs before and after every agent-assisted dependency modification; alert on any newly introduced package
  • Monitor for agent-suggested packages with zero or very low download history at time of suggestion — primary hallucination indicator
  • Scan all agent-proposed dependency changes against OSV, NVD, and GitHub Advisory databases simultaneously
  • Instrument post-install hooks to detect unexpected network connections, file system writes outside project scope, or process spawning from package scripts
  • Alert on any package name not present in historical dependency graph or approved registry catalog
Responsive Controls
  • Immediately isolate and terminate build environments where unvalidated packages were installed; treat runner as fully compromised
  • Rotate all secrets accessible from compromised build runner environments; enumerate all artifacts built with potentially compromised runners
  • Report newly identified malicious package names to registry security contacts (PyPI Security, npm security) and relevant CERT/CC
  • Audit all downstream artifacts produced by builds that ingested the malicious package for signs of tampering or payload embedding

▶ T-03 Autonomous Agent Privilege Escalation in CI/CD Critical
Preventive Controls
  • Apply strict least-privilege scoping via per-job permissions: blocks in GitHub Actions; never use workflow-level permission grants for agent jobs
  • Enforce OIDC token audience restrictions and subject claim constraints binding tokens to specific repository, branch, and environment context
  • Implement agent permission boundaries as OPA/Kyverno policy enforced at platform level, independent of agent self-reporting or system prompt constraints
  • Prohibit id-token: write in any workflow job involving AI agent execution unless explicitly justified, documented, and security-reviewed
  • Segment cloud IAM roles by pipeline stage; build-time agents must not carry deploy-phase permissions; use separate role chains per stage
Detective Controls
  • Enable GitHub Actions audit logging with SIEM integration; alert on OIDC token requests from agent-driven workflow jobs
  • Monitor cloud IAM activity for role assumptions originating from CI/CD OIDC providers; flag any cross-account or cross-environment assumptions
  • Detect IAM actions outside the expected permission baseline for each pipeline stage using cloud-native access analyzers (AWS IAM Access Analyzer, GCP Policy Analyzer)
  • Correlate pipeline execution timeline with cloud API call logs to surface anomalous access patterns not attributable to documented pipeline steps
Responsive Controls
  • Immediately revoke compromised OIDC token and associated temporary IAM credentials; invalidate the OIDC federation session
  • Isolate affected pipeline runner; preserve complete logs including GitHub Actions runtime environment for forensic analysis
  • Enumerate all API actions performed under the compromised role during the full incident window using cloud provider audit logs
  • Apply emergency SCPs (AWS) or Organization Policies (GCP) to contain blast radius during investigation; scope to minimum required for business continuity
References: LLM06 — Excessive Agency LLM08 — Excessive Permissions SSDF PW.4 SSDF RV.3 SLSA L4 — Hermetic Build
▶ T-04 MCP Server Compromise Leading to Pipeline Takeover Critical
Preventive Controls
  • Implement mutual TLS (mTLS) authentication between orchestration agents and all MCP servers; reject any tool registration from unauthenticated endpoints
  • Cryptographically sign MCP tool schemas at publication time; verify signatures against a trusted key before loading into agent tool registry
  • Maintain allowlists of permitted MCP server identities, tool namespaces, and schema versions; enforce deny-by-default for new registrations requiring explicit approval
  • Isolate MCP server processes with network and filesystem sandboxing; restrict egress to expected upstream systems only via enforced network policy
  • Implement tool call rate limiting and response size limits per MCP server to constrain exploitation surface
Detective Controls
  • Audit all MCP tool invocations with full request/response logging in tamper-evident storage; retain for cross-session correlation and incident investigation
  • Detect schema drift in MCP tool definitions by comparing registered schemas against cryptographically verified last-known-good baselines on each pipeline start
  • Monitor for unexpected tool calls or response patterns inconsistent with the current pipeline stage and declared agent task
  • Alert on MCP server certificate changes, DNS record modifications, or network endpoint alterations outside the approved change window
Responsive Controls
  • Immediately deregister compromised MCP server from all agent tool registries; halt all dependent pipeline runs and block new agent sessions from registering the server
  • Roll back any infrastructure or configuration changes that were initiated during the compromised MCP interaction window
  • Conduct full forensic audit of all tool calls executed via the compromised MCP endpoint; reconstruct the full agent action sequence
  • Re-validate and rotate all agent-accessible secrets and credentials that were within scope during the incident window
References: LLM07 — System Prompt Leakage LLM06 — Excessive Agency SSDF PW.4 SSDF RV.1 SLSA L3 — Non-falsifiable Provenance
▶ T-05 AI-Generated IaC with Embedded Backdoor Secrets Medium
Preventive Controls
  • Enforce pre-commit secret scanning (Gitleaks, TruffleHog, git-secrets) as blocking hard gates on all AI-generated file commits; zero-tolerance for credential-pattern matches
  • Apply IaC-specific static analysis (Checkov, tfsec, KICS) as mandatory pipeline gates before any Terraform plan or CloudFormation deploy operation is permitted
  • Require all agent-generated IaC to pass CIS Benchmark compliance checks and organization-specific policy-as-code before deployment approval is granted
  • Prohibit hardcoded values for credential-class fields in IaC templates; enforce parameterization with secrets manager references (AWS Secrets Manager, HashiCorp Vault) via linting rules
  • Generate AIBOM for all agent-assisted pipeline runs; log model version, prompt hash, and generation timestamp as immutable provenance for every IaC artifact produced
Detective Controls
  • Continuously scan deployed infrastructure against approved configuration baselines using cloud-native tooling (AWS Security Hub, GCP Security Command Center) with IaC origin tagging
  • Correlate deployed resource configurations with their generating IaC artifacts to maintain audit chain integrity and detect post-deploy tampering
  • Monitor for public exposure of resources designated as private: S3 Block Public Access violations, GCS uniform bucket-level access bypass, public RDS snapshots
  • Detect IAM policies with wildcard actions (*), overly broad resource scopes, or missing condition constraints in agent-generated IaC before and after deployment
Responsive Controls
  • Immediately apply restrictive SCPs or Organization Policies to contain exposed resources; block all public access at the organization level pending investigation
  • Rotate any credentials that were hardcoded in deployed IaC; cross-reference access logs for evidence of unauthorized use during the exposure window
  • Destroy and re-provision affected infrastructure from validated, policy-compliant IaC templates with full audit trail; do not attempt in-place remediation of compromised resources
  • Update IaC generation agent system prompts and add explicit IaC linting rules to prohibit the identified anti-patterns from recurrence
References: LLM02 — Insecure Output Handling LLM09 — Overreliance SSDF PW.1 SSDF PS.1 SLSA L2 — Hosted Build Platform
§ 4.0

Implementation Guardrails

Prescriptive, production-actionable security controls for teams deploying autonomous AI agents in DevSecOps pipelines. Each guardrail maps directly to threats identified in § 2.0.

G-01 / Static Analysis Gates
Static Analysis Gates on AI-Generated Code
All code produced by AI agents must pass a mandatory static analysis gate before merge or deployment. Gates must be enforced as branch protection rules — not advisory checks — and must cover security vulnerabilities, AI-specific anti-patterns, and credential material. Agents must not be able to self-approve their own outputs.
  • 01Integrate SAST tooling (Semgrep, CodeQL, Snyk Code) as required status checks on all AI-assisted branches with non-zero exit codes blocking merge
  • 02Define AI-specific rulesets targeting hallucinated stdlib patterns, deprecated API usage, credential anti-patterns, and insecure default configurations
  • 03Configure zero-tolerance exit codes on critical severity findings; automate PR blocking via branch protection API — no manual override path for agent-submitted code
  • 04Run IaC scanners (Checkov, tfsec) in parallel with SAST; map findings to CIS/NIST control IDs in structured reports attached to the PR
  • 05Store all scan results as immutable pipeline artifacts with cryptographic link to the AIBOM record of the generating agent session
# .github/workflows/ai-sast-gate.yml on: [pull_request] jobs: ai-code-gate: runs-on: ubuntu-latest permissions: contents: read # minimal — no write security-events: write # SARIF upload only steps: - uses: semgrep/semgrep-action@v1 with: { config: "p/ai-generated-code-security" } - run: checkov -d . --framework all --hard-fail-on HIGH
G-02 / Dependency Validation
Dependency Validation Pipeline (OSSPolicyGuard Pattern)
Every dependency suggested or introduced by an AI agent must traverse a multi-signal validation pipeline before installation. The OSSPolicyGuard pattern applies policy-as-code evaluation across package existence, reputation signals, vulnerability status, and provenance attestation — blocking agent-initiated installs that fail policy thresholds.
  • 01Verify package existence and canonical name on target registry before any install operation; reject non-existent packages without human escalation
  • 02Evaluate OpenSSF Scorecard score, publish date, maintainer count, and download velocity as weighted risk signals against configurable policy thresholds
  • 03Cross-reference against OSV, NVD, and GitHub Advisory databases; block packages with CVSS ≥ 7.0 vulnerabilities without explicit documented exception
  • 04Require SLSA provenance attestation (L2+) for all new production dependencies; reject packages lacking verifiable build provenance
  • 05Route failed validations to human security reviewer with full risk report; log all decisions with agent session ID for traceability
# OSSPolicyGuard policy — policy.rego package ai_dependency_policy default allow = false deny[msg] { input.pkg.publish_days < 30 msg := "Package age <30d: hallucination risk" } deny[msg] { not input.pkg.registry_verified msg := "Package not in approved registry" } deny[msg] { input.pkg.max_cvss > 7.0 msg := "CVE score exceeds policy threshold" }
G-03 / Permission Boundaries
Agent Permission Boundaries — Least-Privilege Scoping
Autonomous agents must operate under explicitly defined, minimally-scoped permission boundaries enforced at the platform level — not self-asserted by the agent or declared in system prompts. Permissions must be scoped to the minimum required for each specific pipeline stage and automatically expire at task completion.
  • 01Define agent permission profiles per pipeline role (read-only audit, write-on-branch, deploy-to-staging) as versioned policy-as-code artifacts reviewed by security team
  • 02Use GitHub Actions job-level permissions: blocks with minimum required scopes; explicitly set unused permissions to none — do not rely on defaults
  • 03Issue time-bounded OIDC tokens (TTL ≤ 15 minutes) for cloud operations; bind subject claim to specific repository, branch, and environment — reject overly broad subject claims
  • 04Enforce network egress allowlists for agent runner environments; deny all unlisted external endpoints via firewall rules independent of agent configuration
  • 05Implement automated permission drift detection: continuously compare effective agent permissions against declared baseline; alert and block on any excess
# GitHub Actions least-privilege template permissions: # job-level block contents: read # read repo only pull-requests: write # only if review agent id-token: none # explicit OIDC deny packages: none deployments: none secrets: none # no secret inheritance
G-04 / Human-in-the-Loop
Human-in-the-Loop Checkpoints for High-Risk Actions
Fully autonomous agent operation must be bounded by mandatory human review gates at defined risk thresholds. The high-risk action taxonomy must be maintained as a versioned, externally-enforced policy artifact — not embedded in agent prompts where it can be overridden by injection attacks.
  • 01Enumerate and version-control the high-risk action taxonomy: infrastructure destroy, secret rotation, permission grants, external publishing, cross-environment promotion
  • 02Implement platform-enforced approval gates using GitHub Environments with required reviewer assignments; agent cannot self-approve or bypass the environment gate
  • 03Surface agent confidence scores, reasoning chain, and relevant context to human reviewers in structured, actionable format — not raw LLM output
  • 04Implement time-boxed automatic escalation: if no human response within defined SLA window, automatically block the action and page on-call security engineer
  • 05Log all human approval and rejection decisions with rationale and reviewer identity; include in AIBOM as part of the immutable audit trail for compliance reporting
G-05 / AIBOM
AIBOM — AI Bill of Materials for Agent-Assisted Pipelines
All pipeline artifacts produced with AI agent assistance must be accompanied by an AI Bill of Materials (AIBOM) documenting the AI components, model versions, prompt templates, and tool configurations involved in their generation. AIBOM enables reproducibility, compliance audit, and post-incident forensic investigation.
  • 01Record model name, version, API endpoint, temperature, and max tokens for every agent invocation; store as structured metadata alongside produced artifacts
  • 02Compute and store a cryptographic hash (SHA-256) of the system prompt, tool configuration, and memory state at time of invocation — treat prompt changes as security-relevant events
  • 03Link AIBOM records to produced artifacts using in-toto attestation framework; embed attestation in artifact metadata or publish to transparency log
  • 04Include AIBOM alongside traditional SBOM in all release manifests; expose both as queryable APIs for downstream consumers and compliance tooling
  • 05Require AIBOM verification as a hard deployment gate for regulated environments (FedRAMP, PCI DSS, ISO 27001, SOC 2 Type II)
# AIBOM attestation (in-toto / SLSA predicate) _type: "https://in-toto.io/Statement/v0.1" subject: [{ name: "artifact.tar.gz", digest: { sha256: "..." }}] predicateType: "https://aibom.dev/predicate/v0.1" predicate: model: <model>@<version> promptHash: "sha256:3f8a9c..." toolConfig: "sha256:9c2b1d..." invokedAt: 2026-08-08T00:00:00Z reviewer: "human-approved"
G-06 / MCD Pattern
Malicious Code Detection at Pipeline Ingestion Points
The Malicious Code Detection (MCD) pattern mandates independent inspection of all AI-generated artifacts at each pipeline ingestion boundary before processing. This defense-in-depth layer operates independently of the agent's own security assessments — closing the gap where a compromised agent cannot detect its own malicious outputs.
  • 01Deploy independent MCD hooks at every pipeline ingestion boundary: commit, PR merge, artifact upload, and deployment trigger — no boundary is exempt
  • 02Run multi-engine scanning in independent parallel tracks: SAST, secret detection, malware signature matching, and behavioral analysis — store each engine's results separately
  • 03Apply behavioral analysis to IaC artifacts: detect exfiltration patterns (unexpected data sinks), unusual outbound connection specifications, and anomalous IAM constructs
  • 04Apply Shannon entropy analysis to all AI-generated files to detect potential encoded payloads, obfuscated strings, or compressed malware embedded in generated content
  • 05Cross-correlate MCD findings with AIBOM records to identify whether specific model versions, prompt configurations, or agent sessions are associated with elevated detection rates
# MCD pipeline hook configuration hooks: pre-merge: - trufflehog filesystem . --entropy-threshold=4.5 - semgrep --config=p/malicious-code --error - checkov -d . --framework=all --hard-fail-on HIGH - gitleaks detect --source . --exit-code 1 on-finding: action: block_and_quarantine notify: security-oncall retain: 90d # forensic retention
